## 2. ⚠️ 重要发现：我的重启脚本**自己把自己杀了**

### 2.1 日志证据

`restart-dsh-3080.log` 到此为止：

```
[12:31:01] killed PID 127888 (node)
```

**`killed` 之后什么都没有** —— 没有 `port released`，没有 `started new instance`，
子进程的 stdout/stderr 文件**根本没被创建**。

### 2.2 原因

脚本第 2 步会**连父进程一起结束**（本意是防止 `npx` 监督进程重新拉起旧的子进程）：

```powershell
$parentId = (Get-CimInstance Win32_Process -Filter "ProcessId=$oldPid").ParentProcessId
foreach ($target in @($oldPid, $parentId)) { Stop-Process -Id $target -Force }
```

而**我的工具调用链本身就在那棵树里** —— 上一轮我已经误杀过自己的
`dsh-subprocess-local/runner.js` 一次。这次同理：

```
npx (49772)
└─ dsh web (127888)          ← 被 kill
   └─ ... 我的 shell / 脚本    ← 顺带被杀
```

**脚本把自己所在的进程树一起杀了**，所以后续步骤（第 3~6 步：等待端口释放、启动新实例、校验）
**永远不会执行**。

## 3. 教训

### 3.1 「自我重启」是结构性问题，不能靠同一个进程树

**任何从"被重启的服务"进程树内发起的重启，都无法完成重启自己。**

这与"延迟启动"或"分离进程"无关 —— 只要新进程仍是旧进程的**子进程**，
杀掉旧进程时它就会一起死。

**正确做法（按可靠性排序）**

| 方案 | 说明 |
|---|---|
| **① Windows 任务计划程序** | 真正独立于进程树，最可靠 |
| ② `schtasks` 一次性任务 | 同上，脚本化即可 |
| ③ 启动一个**父进程已死**的进程 | 例如经 `WMI`/服务启动；PowerShell 里很难保证 |
| ④ **不由服务自身发起** | 让人在另一个终端执行 —— **最省事且最明确** |

⚠️ `Start-Process -WindowStyle Hidden` **不是**充分隔离 —— 子进程仍在父进程的作业/进程树里。

### 3.2 不要"连父进程一起杀"

我当初加这个是为了防止 `npx` 监督进程把旧子进程拉回来。
但这会把**发起者自己**也带走。更稳的做法是：

- 只杀监听端口的那个 PID
- 若担心监督进程重拉，**先停监督进程，再停子进程**，且**由外部执行**

### 3.3 先看完整命令行，再决定杀谁

本轮内我已因此误杀一次自己的 `runner.js`。
判断"这是不是孤儿进程"时，**必须看完整 `CommandLine`**，不能只看启动时间。

## 4. 对启动器（Phase 5）的直接影响

启动器**要自己拉起 `dsh web`**，所以它必然会遇到"重启/关闭"的问题。上面的教训直接适用：

1. **启动器不能是 `dsh web` 的子进程** —— 否则它无法管理/重启自己的服务端
2. 正确结构：**启动器是父进程，`dsh web` 是它的子进程**
   - 启动器负责：拉起、抓 token、监控、退出时清理
   - 这样"重启"= 杀子进程 + 再拉一个，母体存活，自然可行
3. ⚠️ 启动器若在退出时清理子进程，要确保**自己先不成为被清理的那个**

> 这正好说明为什么启动器应做成**独立 exe 作为父进程**，
> 而不是"在 DSH 里面跑一个插件去管 DSH"。
